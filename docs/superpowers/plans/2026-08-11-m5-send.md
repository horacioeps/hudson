# Hudson M5 — Send (Outbox) Implementation Plan

> **For agentic workers:** implemented via a Workflow that runs each task as implement → adversarial-review → fix, sequentially in this worktree. Steps use checkbox syntax.

**Goal:** Correct RFC 5322 sends with bulletproof dedup, reply threading, and an undo-send hold — the headless Outbox foundation behind `hudson send`/`reply` (UI composer is a later U-milestone).

**Architecture:** New `Outbox` library target (MIME building + send state machine), a `send_jobs` durable queue in `Store` (mirrors the existing `mutation_queue` durability pattern), a `messages.send` upload endpoint in `GmailKit`, and a send-flusher that runs the `pending → held → in_flight → sent` state machine with a restart dedup probe. Source of truth: spec `docs/superpowers/specs/2026-08-10-hudson-foundation-design.md` §7 (Outbox) and §7.3 (dedup), and `docs/superpowers/design/2026-08-10-speed-ai-architecture.md` "M5 — Send". Every implementer MUST read those two sections.

**Tech Stack:** Swift 6 strict concurrency, GRDB 7, swift-argument-parser. No new external deps. Swift Testing. Match house readability (WHY-comments, full-word names) — see `Sources/Store/MutationQueue.swift` and `Sources/SyncEngine/MutationFlusher.swift` as the pattern to mirror.

## Global Constraints

- **Swift 6 strict concurrency.** Actors for anything with mutable state driven by the network (mirror `MutationFlusher` — an `actor`). Store access via the existing `async` APIs; no sync writer access off-actor.
- **Two external deps only** (swift-argument-parser, GRDB). Foundation is fine.
- **Dedup is our job (Gmail has NO idempotency token).** The dedup protocol in §7.3 is the load-bearing invariant: UUID `Message-ID` assigned at ENQUEUE (persisted on the job row); state machine transitions `in_flight` committed to SQLite BEFORE the network call; on restart of an `in_flight` job of unknown outcome, probe `messages.list q=rfc822msgid:<id> in:sent` and skip if found — a fast MISS is NOT proof of non-delivery, so ambiguous outcomes wait and re-probe rather than resend. This must be provable under kill-between-send-and-record (the spec's stated biggest M5 risk).
- **Threading triple (§7.1):** a reply is correctly threaded only with ALL THREE — Gmail `threadId` on the send call, RFC-compliant `References`/`In-Reply-To` headers, AND a matching normalized `Re:` Subject. An edited subject deliberately OMITS `threadId` (starts a new thread). Golden-file tests assert all three.
- **Size validation at enqueue, never at fire time (§7.1):** the 35 MB MIME cap (~25 MB attachments after base64) is validated when the message is composed/enqueued, not when a scheduler later fires it.
- **Sends use the M3 `post`/upload core** (`GmailClient`), and the interactive `QuotaBucket` lane (`messages.send` = 100 quota units, §5/§6). No new HTTP stack.
- **Privacy #1 unchanged:** sending is user-initiated; no background/auto-send, no AI here.
- **Readability bar (open-source):** WHY-comments, focused files, full-word names.

## Task 1: Store — `send_jobs` durable queue (migration v7 + SendQueue API)

**Read first:** spec §7.3 (state machine + dedup), and `Sources/Store/MutationQueue.swift` (the durability/claim pattern to mirror).

**Files:** Create `Sources/Store/SendQueue.swift`; modify `Sources/Store/Migrations.swift` (append `v7`); test `Tests/StoreTests/SendQueueTests.swift`.

**Interfaces (Produces):**
- `public enum SendJobState: String, Sendable { case pending, held, inFlight = "in_flight", sent, failed }`
- `public struct SendJob: Sendable, Equatable { public let id: Int64; public let account: String; public let rfc822MessageID: String; public let threadID: String?; public let rawMIME: Data; public let state: SendJobState; public let holdUntil: Int64; public let enqueuedAt: Int64; public let sentMessageID: String? }`
- On `HudsonDatabase`:
  - `func enqueueSend(account:rfc822MessageID:threadID:rawMIME:holdUntil:now:) async throws -> Int64` (inserts `pending`)
  - `func claimSendable(account:now:) async throws -> [SendJob]` — jobs whose `state IN ('pending','held')` and `hold_until <= now`, oldest first (past the undo-hold, ready to send).
  - `func markSendInFlight(id:account:) async throws` — `pending/held → in_flight` (this is the transition that MUST be committed before the network call).
  - `func markSent(id:account:sentMessageID:) async throws`; `func markSendFailed(id:account:) async throws`.
  - `func inFlightSendJobs(account:) async throws -> [SendJob]` — for the restart dedup probe.
  - `func cancelSend(id:account:now:) async throws -> Bool` — deletes the job ONLY if still `pending`/`held` and `hold_until > now` (undo-send); returns whether it cancelled.

**Migration v7** creates `send_jobs(id INTEGER PRIMARY KEY, account_email TEXT NOT NULL, rfc822_message_id TEXT NOT NULL, thread_id TEXT, raw_mime BLOB NOT NULL, state TEXT NOT NULL DEFAULT 'pending' CHECK(state IN ('pending','held','in_flight','sent','failed')), hold_until INTEGER NOT NULL, enqueued_at INTEGER NOT NULL, sent_message_id TEXT)` + a UNIQUE index on `(account_email, rfc822_message_id)` (dedup guard) + an index on `(account_email, state, hold_until)`.

**Steps (TDD):** failing test (enqueue→claim excludes held-in-future; markInFlight transitions; cancel only while held; unique rfc822 id) → migration + API → pass → commit `feat(store): send_jobs durable queue (migration v7) + SendQueue API`.

## Task 3: Outbox target + MimeBuilder (RFC 5322 + threading triple + size validation)

**Read first:** spec §7.1 (MIME + threading triple + size limits). Add the `Outbox` target to `Package.swift` (deps: `GmailKit`, `Store`; product library) + `OutboxTests` test target.

**Files:** `Sources/Outbox/OutboxMessage.swift`, `Sources/Outbox/MimeBuilder.swift`, `Sources/Outbox/SubjectNormalization.swift`; tests `Tests/OutboxTests/MimeBuilderTests.swift`, `Tests/OutboxTests/SubjectNormalizationTests.swift`, golden files under `Tests/OutboxTests/Golden/`.

**Interfaces (Produces):**
- `public struct Attachment: Sendable, Equatable { public let filename: String; public let mimeType: String; public let data: Data }`
- `public struct OutboxMessage: Sendable { from, to:[String], cc:[String], bcc:[String], subject: String, bodyText: String, bodyHTML: String?, attachments:[Attachment], inReplyTo: String?, references:[String], threadID: String? }` (memberwise public init).
- `public enum MimeBuilder { public static func build(_ m: OutboxMessage, messageID: String, date: Date) throws -> Data; public static let maxEncodedBytes = 35 * 1024 * 1024 }` — deterministic output given `messageID`+`date` (so golden files are stable; the caller passes both). `text/plain` + `text/html` as `multipart/alternative`; attachments wrap that in `multipart/mixed`. Sets `Message-ID`, `Date`, `From`, `To`/`Cc`, `Subject`, and — when `inReplyTo`/`references` present — `In-Reply-To`/`References`. Throws `OutboxError.tooLarge(encodedBytes:)` when base64-encoded size exceeds `maxEncodedBytes`.
- `public enum SubjectNormalization { public static func replySubject(from original: String) -> String }` — one normalized `Re: ` prefix, tolerating existing `Re:`/`AW:`/`SV:`/`RE:` (case-insensitive, possibly repeated) → collapses to a single `Re: `.

**Steps:** failing golden-file tests (a plain reply's bytes match a committed golden incl. all threading headers + normalized subject; an attachment message is `multipart/mixed`; oversized throws) + subject-normalization table tests → implement → pass → commit `feat(outbox): MIME builder (threading triple, size validation) + subject normalization`.

Note: keep MIME output BYTE-DETERMINISTIC for a fixed `messageID`/`date` (fixed boundary strings derived from `messageID`, no random). This is what makes golden files viable — see the Global Constraint on determinism.

## Task 4: Outbox SendService — enqueue + flush state machine + restart dedup probe

**Read first:** spec §7.3 fully; `Sources/SyncEngine/MutationFlusher.swift` (actor flusher pattern, cursor-gated retire — mirror its structure).

**Files:** `Sources/Outbox/SendService.swift`; test `Tests/OutboxTests/SendServiceTests.swift` (with a scripted/fault-injecting Gmail double — mirror `Tests/SyncEngineTests/Support/ScriptedGmail.swift`).

**Interfaces (Produces):**
- `public actor SendService` with `init(api:database:account:)` (api = a protocol the `GmailClient` conforms to, so tests inject a double — define `public protocol SendTransport { func sendRawMessage(_:threadID:) async throws -> SentMessage; func findSentMessageID(rfc822MessageID:) async throws -> String? }` and conform `GmailClient`).
  - `func enqueue(_ message: OutboxMessage, undoHold: Duration = .seconds(15), now: Int64) async throws -> Int64` — assign a UUID-based `Message-ID` (`<uuid@hudson.local>` or the sender's domain), build+validate the MIME (size), compute `holdUntil = now + undoHold`, persist via `enqueueSend`. Returns the job id (for undo).
  - `func cancel(jobID: Int64, now: Int64) async throws -> Bool` — delegates to `cancelSend` (undo-send).
  - `func flushOnce(now: Int64) async throws -> Int` — the state machine: (1) restart safety — for each `inFlightSendJobs`, run the dedup probe; if `findSentMessageID` returns an id → `markSent`; if a definitive draft/absence signal says not sent → resend; if AMBIGUOUS (fast miss) → leave `in_flight` and return (re-probe next flush), never resend. (2) `claimSendable(now:)` → for each: `markSendInFlight` (COMMIT) → `sendRawMessage` → `markSent(sentMessageID:)`; on send error, leave `in_flight` for the next flush's probe path (do NOT immediately resend). Returns count sent.

**Steps:** failing tests: (a) happy path enqueue→flush marks sent; (b) undo cancels before hold elapses, not after in_flight; (c) **kill-between-send-and-record**: a job left `in_flight` whose Message-ID IS found by the probe is marked sent, NOT resent (the core dedup proof); (d) ambiguous probe miss does not resend. → implement → pass → commit `feat(outbox): SendService — enqueue, undo-hold, flush state machine + restart dedup probe`.
